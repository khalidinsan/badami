## Summary

| Severity | Count |
|---|---|
| Critical | 4 |
| High | 7 |
| Medium | 19 |
| Low | 14 |

The three critical findings compound with each other: credentials are protected by a key an attacker can recompute, that ciphertext is synced to a remote cloud database, and the webview has no CSP while holding filesystem-wide read permission.

**What is already done well:** AES-256-GCM (correct AEAD) with fresh `OsRng` nonces per encryption and no nonce reuse; Argon2id for the master-password path at adequate cost (64 MiB, t=3); the Turso sync token correctly stored in the OS keychain; `local_dev` config generation properly validates site names/TLDs and shell-escapes all osascript paths; all subprocesses use argv rather than `bash -c`; TypeScript `strict` mode on and `tsc --noEmit` passes clean; only 30 `as any` casts across 73k LOC; no `dangerouslySetInnerHTML`, `eval`, or `innerHTML` injection sinks anywhere.

## CRITICAL

### C1. SSH private keys are encrypted with a key derived from public data

`src-tauri/src/commands/credential.rs:114-137`

```rust
let mut hasher = DefaultHasher::new();
SERVICE_NAME.hash(&mut hasher);                            // "Badami" — public constant
if let Ok(name) = hostname::get() {
    name.to_string_lossy().to_string().hash(&mut hasher);  // hostname — not secret
}
let h1 = hasher.finish();
...
key[..8].copy_from_slice(&h1.to_le_bytes());
key[8..16].copy_from_slice(&h2.to_le_bytes());
key[16..24].copy_from_slice(&h1.to_be_bytes());  // byte-reversal of h1 — adds no entropy
key[24..32].copy_from_slice(&h2.to_be_bytes());
```

`DefaultHasher` is SipHash-1-3, a **non-cryptographic** hash. Both inputs are public. `h2` is derived deterministically from `h1`, and the second half of the key is just the byte-reversal of the first — so the 256-bit key collapses to a function of the hostname with at most ~64 bits of real entropy, and zero secret entropy against anyone who knows the hostname.

This key protects **SSH private keys** (`pem_keys.encrypted_data`). Anyone holding the database file plus the hostname recomputes the key and decrypts every stored key.

Latent data-loss bug in the same function: Rust does not guarantee `DefaultHasher`'s algorithm is stable across compiler versions or platforms. A toolchain upgrade silently renders every stored PEM key permanently undecryptable.

**Fix:** Delete `derive_master_key()`. Store PEM key material directly in the OS keychain via the `keyring` crate already used in this same file, or route it through the vault key path once C2 is fixed.

### C2. Blast radius: the ciphertext is synced to a remote cloud database

`src/db/migrations/006_server_module.sql:27-30`, `src-tauri/src/commands/db.rs:262-273`

`pem_keys.encrypted_data BLOB` lives in `badami.db` under `app_data_dir()`. When sync is enabled, `db_init` opens that database as a **libsql embedded replica**, which synchronizes the entire database to Turso — every table, including `pem_keys`, `credentials`, and `settings`.

The result: SSH private keys, protected only by the hostname-derived key from C1, are uploaded to a remote server. An attacker with the Turso replica (a leaked sync token, a compromised Turso account, or the provider itself) plus a guessable hostname recovers the plaintext keys.

**Fix:** Blocked on C1. Additionally, consider excluding secret-bearing tables from sync, or encrypting them under a key that never leaves the local keychain.

### C3. Null CSP + filesystem-wide read + global Tauri API

`src-tauri/tauri.conf.json:13,26` and `src-tauri/capabilities/default.json:10-24`

```json
"withGlobalTauri": true,
"security": { "csp": null }
```

```json
{ "identifier": "fs:allow-read", "allow": [ { "path": "**" }, ... ] }
```

Three settings that are individually defensible combine into a full-compromise path:

1. `csp: null` — no content-security-policy on the webview.
2. `withGlobalTauri: true` — `window.__TAURI__` reachable from any script in the page.
3. `fs:allow-read` scoped to `**` — unrestricted read of the entire filesystem, granted to all three windows (`main`, `today`, `search`).

This application renders untrusted remote content by design: HTTP response bodies in the API client, file contents over SFTP, database cell values, SSH terminal output. Any script-injection sink in that content gets `window.__TAURI__` and can read `~/.ssh/*`, `badami.db`, browser profiles, or anything else on disk — and can invoke `ssh_connect`, `credential_decrypt_field`, and `shell:open` directly.

The three `fs` path entries are redundant; `**` supersedes `$HOME/**` and `/Users/**`.

**Fix:** Set a real CSP, e.g. `default-src 'self'; connect-src 'self' https://openrouter.ai; img-src 'self' data: asset: https://asset.localhost; style-src 'self' 'unsafe-inline'`. Remove the `**` fs scope and rely on dialog-returned paths (auto-granted per session) plus a narrow temp-dir scope. Consider dropping `withGlobalTauri` in favour of importing the JS API.

### C4. A malicious SSH/SFTP server can write arbitrary files on the local machine

`src-tauri/src/lib.rs:27-31` reached from `src/components/server/FileManager.tsx:178-179`

```rust
#[tauri::command]
fn ensure_temp_dir(filename: String) -> Result<String, String> {
    let dir = std::env::temp_dir().join("badami-fm");
    std::fs::create_dir_all(&dir).map_err(|e| format!("Failed to create temp dir: {e}"))?;
    Ok(dir.join(&filename).to_string_lossy().into_owned())   // filename unsanitized
}
```

```ts
const localPath = await invoke<string>("ensure_temp_dir", { filename: entry.name });
await fm.download(entry.path, localPath);
```

`entry.name` comes from the **remote server's directory listing** — fully attacker-controlled when connecting to a malicious or compromised host. `Path::join` does not reject `..`, so a listing entry named `../../../../Users/<user>/.zshrc` yields a path outside the temp directory, and `fm.download` then writes the remote file's contents there.

This is remote-server-to-local-arbitrary-file-write. Writing `~/.zshrc`, `~/.ssh/authorized_keys`, or a LaunchAgent plist converts it into local code execution the next time a shell opens. It requires only that the user click "open in editor" on a file in a listing.

**Fix:** In `ensure_temp_dir`, keep only the final path component and reject any input containing a path separator, a `..` component, or an absolute prefix. Validate on the Rust side — the frontend cannot be trusted to sanitize a remote-supplied name.

## HIGH

### H1. No SSH host key verification anywhere — MITM and credential theft

`src-tauri/src/commands/ssh.rs:98-100`, `sftp.rs:128-130`, `session_manager.rs:26-27`

```rust
session.set_tcp_stream(tcp);
session.handshake().map_err(|e| format!("SSH handshake failed: {}", e))?;
// → proceeds directly to userauth_password / userauth_pubkey_memory
```

A grep for `known_hosts`, `host_key`, and `check_host` across all of `src-tauri/src` returns nothing. The `ssh2` crate does not verify host keys on its own — the caller must do it. All three connect paths authenticate immediately after the handshake without ever inspecting the server's key.

Any machine-in-the-middle presents its own key and the client proceeds. With `auth_type == "password"` (`ssh.rs:107`, `sftp.rs:137`, `session_manager.rs:33`) the cleartext password is handed straight to the attacker, and every session is transparently relayable.

**Fix:** After `handshake()`, call `session.host_key()` and check it against a persisted known-hosts store. Trust-on-first-use is acceptable: pin on first connect, hard-fail on mismatch, prompt on unknown. Apply to all three paths.

### H2. Vault default mode — Argon2id over entirely public inputs with a static salt

`src-tauri/src/commands/vault.rs:52-67`, `:10`

```rust
const APP_SECRET: &str = "badami-credential-vault-v1";
let input = format!("{APP_SECRET}:{hostname}");
let salt = b"badami-machine-salt-v1";
```

This is the mode the app starts in — `VaultState::new()` (`vault.rs:27-35`) seeds the key from `derive_machine_key()` with `has_master_password: false`. The KDF choice and cost are correct, but every input is public or guessable, so Argon2id adds no protection: anyone with the SQLite file and the hostname recomputes the key and decrypts all credentials.

The static salt compounds it — two machines with the same hostname share a vault key, and keys are precomputable across installs.

**Fix:** In no-master-password mode, generate a random 32-byte key at first run and store it in the OS keychain. Real protection should not be gated behind an optional master password.

### H3. SQL injection via incomplete escaping — malicious CSV yields arbitrary DML

`src-tauri/src/commands/db_transfer.rs:289`, `db_data.rs:485-495`

```rust
format!("'{}'", val.replace('\'', "''"))
```

Only single quotes are doubled; **backslashes are not escaped**. Under MySQL's default `sql_mode` (which does not include `NO_BACKSLASH_ESCAPES`), backslash is a string escape character. A value ending in `\` produces `'\'`, where `\'` is an escaped quote — the string literal never closes and the following SQL is reinterpreted as code.

The strongest vector is `dbc_import_csv` (`db_transfer.rs:285-299`), which concatenates cell text from an **attacker-supplied CSV file** into `INSERT` statements. Opening a malicious CSV executes arbitrary DML against whatever database the user is connected to.

The same defect appears in `json_to_sql_literal` (`db_data.rs:491`), reached from `dbc_update_cell` (`:354`), `dbc_insert_row` (`:411`), and `dbc_delete_rows` (`:453`), and in the SQL exporter (`db_transfer.rs:156`).

Note the threat model: `dbc_query` / `dbc_execute` / `dbc_execute_ddl` accept raw SQL by design (they back the SQL editor) and are not flagged. The finding is specific to the *data-driven* builders.

**Fix:** Stop building value literals as strings. Use `sqlx` bind parameters (`.bind()`) for MySQL/Postgres and libsql positional params for SQLite in `update_cell` / `insert_row` / `delete_rows` and the CSV importer.

### H4. `kill()` accepts out-of-range PIDs that cast to negative — signal broadcast

`src-tauri/src/commands/local_dev/supervisor.rs:210,217` and `mariadb_guard.rs:344-345,351,358`

```rust
if pid == 0 { return Err(format!("refusing {name} to pid 0")); }   // only guard
let rc = unsafe { kill(pid as i32, sig) };
```

```rust
pub fn read_pid_file(path: &Path) -> Option<u32> {
    let s = fs::read_to_string(path).ok()?;
    s.trim().parse().ok()          // no range check
}
```

PID files are parsed as `u32` with no upper bound. Any value in `2147483648..=4294967295` casts to a **negative** `i32`. In POSIX, `kill(-1, sig)` signals every process the caller may signal, and `kill(-N, sig)` signals process group `N`.

The liveness guard does not help — `pid_is_alive(0xFFFFFFFF)` calls `kill(-1, 0)`, which returns `0`, so the PID reports as alive, `stop_one` proceeds (`supervisor.rs:1393-1397`), and `signal_term` broadcasts `SIGTERM` to all of the user's processes.

Triggered by a truncated or garbage PID file, or by any same-user process writing `4294967295` into `local-dev/pids/*.pid` — or into a MariaDB datadir PID file, which may be foreign.

**Fix:** Reject `pid == 0 || pid > i32::MAX as u32` in both `signal_pid` and `pid_is_alive`, and validate the range in `read_pid_file`.

### H5. Privileged nginx stop SIGKILLs a pre-authorization PID as root

`src-tauri/src/commands/local_dev/supervisor.rs:728,738-739`

```rust
let master_pid = find_our_nginx_master(spec).unwrap_or(0);
// ... later, embedded into the osascript body:
//   kill -TERM "$MASTER" ... ; kill -9 "$MASTER"
```

`MASTER` is resolved *before* `osascript ... with administrator privileges` displays the macOS authentication dialog. The user may take many seconds to type their password. During that window the nginx master can exit and its PID be reused by an unrelated — possibly system — process, which the root shell then `kill -9`s.

**Fix:** Re-resolve the master *inside* the privileged shell by config-path or binary identity immediately before signalling, rather than passing a numeric PID captured before authentication.

### H6. Secrets stored in plaintext in the cloud-synced database

`src/stores/settingsStore.ts:29-38`, `src/hooks/useAiChat.ts:73`, `src/hooks/useApiRequest.ts:190-203`

The OpenRouter API key is written to the `settings` table as a raw string and read back with `getSetting("openrouter_api_key", "")`. Unlike the Turso sync token — which is correctly kept in the keychain (`db.rs:1115-1121`) — this key sits in plaintext on disk and, per C2, syncs to Turso.

Separately, `useApiRequest` writes full request headers and bodies plus complete response bodies to `api_history` in plaintext. Response bodies from an API client routinely contain bearer tokens, session cookies, and PII. Combined with C3's filesystem-wide read, these are trivially exfiltratable.

**Fix:** Move the LLM API key to the keychain alongside the sync token. Redact `Authorization`/`Cookie` headers from history entries, cap stored body size, or gate history behind the vault.

### H7. Changing the master password can destroy the entire vault

`src/hooks/useMasterPassword.ts:110-135`, `src-tauri/src/commands/vault.rs:130-144`

```ts
// Unlock first (verifies current password + puts key in memory)
await invoke("vault_unlock", { password: currentPassword, salt });
const decrypted = await decryptAllSensitiveData();
const newSalt = await invoke<number[]>("vault_set_master_password", { password: newPassword });
await reEncryptAllData(decrypted);
await credentialQueries.updateVaultConfig({ password_hint: newHint || null, argon2_salt: newSalt });
```

Two independent defects compound here.

**The comment is false.** `vault_unlock` performs no verification whatsoever (see M1). A user who mistypes their *current* password proceeds past this line with a garbage key. `decryptAllSensitiveData()` then fails or yields garbage, and the flow continues into re-encryption.

**The rotation is not atomic.** `vault_set_master_password` swaps the live encryption key immediately and merely *returns* the new salt. Every row is then re-encrypted one at a time, and only afterwards is `argon2_salt` persisted to `vault_config`. A crash, quit, or thrown error anywhere in `reEncryptAllData` leaves rows encrypted under a key whose salt was never written anywhere on disk — unrecoverable, because the salt is required to re-derive the key.

**Fix:** Fix M1 first so the current password is genuinely verified. Then move to envelope encryption: a random data key wrapped by the password-derived KEK. Rotation then rewrites a single wrapped-key blob atomically instead of touching every row, and a crash mid-rotation is harmless.

## MEDIUM

### M1. `vault_unlock` never verifies the master password — silent data loss

`src-tauri/src/commands/vault.rs:114-125`

```rust
let key = derive_master_password_key(&password, &salt);
inner.encryption_key = Some(key);
inner.is_locked = false;    // set unconditionally
```

Any password "unlocks" the vault and installs a key. Wrongness surfaces only later, when an AEAD decrypt fails. `vault_get_status` reports unlocked. Worse, a credential *created* after a mistyped unlock is encrypted under the wrong key and becomes undecryptable with the correct password — silent, permanent data loss.

**Fix:** On set-master-password, encrypt a known sentinel value and persist it. On unlock, decrypt-and-verify the sentinel before accepting the key; return an explicit "invalid password" error otherwise.

### M2. RemoteIDE calls two Tauri commands that do not exist

`src/components/server/ide/RemoteIDE.tsx:78-79,115-116`

```ts
const pemKey = await invoke<{ content: string; iv: string }>("get_pem_key_content", { keyId: server.pem_key_id });
pemContent = await invoke<string>("decrypt_pem_content", { encrypted: pemKey.content, iv: pemKey.iv });
```

Neither `get_pem_key_content` nor `decrypt_pem_content` is registered in `lib.rs`. A systematic diff of every `invoke()` name in the frontend against the `generate_handler!` list found exactly three unmatched names: these two, plus `greet` (which lives only in the dead scaffold `App.tsx`, see L1).

The consequence: opening the Remote IDE against a server using `pem_saved` authentication always throws, on both the mount path and the reconnect path. The feature is completely broken for that auth type.

The working pattern is in `SshTerminal.tsx:184-190`:

```ts
const pemKey = await serverQueries.getPemKeyById(server.pem_key_id);
pemContent = await invoke<string>("decrypt_pem_key", {
  encryptedData: pemKey.encrypted_data,
  iv: pemKey.iv,
});
```

**Fix:** Replace both call sites with the `SshTerminal` pattern — note the parameter names differ too (`encryptedData`/`iv`, not `encrypted`/`iv`).

### M3. RemoteIDE leaks backend SFTP and SSH sessions on unmount

`src/components/server/ide/RemoteIDE.tsx:104-153`

The mount effect calls `sftp_connect` and `ssh_connect`; the cleanup is only `return () => { cancelled = true; }`. Neither `sftp_disconnect` nor `ssh_disconnect` is called, so closing the IDE tab leaves both sessions open on the Rust side indefinitely.

It also lacks the StrictMode guard its siblings use (`connectedRef` in `FileManager.tsx:92-94`, `connectedForRef` in `SshTerminal.tsx:244`), so a dev double-mount opens two sessions.

**Fix:** Disconnect both sessions in cleanup and guard the connect with `connectedRef`.

### M4. Root kill by command-line substring match

`src-tauri/src/commands/local_dev/supervisor.rs:741-747`

```sh
for p in $(ps -axo pid=,command= | awk '/nginx: master process/ && /local-dev\/nginx/ {print $1}'); do kill -TERM "$p"; done
```

Runs as root and targets any process whose argv merely *contains* both substrings. A same-user process can craft such an argv. Combined with the scan-then-kill PID-reuse window, this lets an unprivileged process influence which PID a root shell kills.

**Fix:** Match on verified binary identity (`proc_pidpath` equals the Badami nginx path) rather than an argv regex, and never `kill -9` by substring as root.

### M5. Non-nginx stop paths signal the PID file without an identity check

`src-tauri/src/commands/local_dev/supervisor.rs:1384,1396`, `:1300-1302`

`signal_quit(p)` (php-fpm), `signal_term(p)` (generic), and the MariaDB SIGTERM all take `p` straight from `read_pid_file`. Only nginx verifies process identity, via `find_our_nginx_master` / `proc_pidpath`. If a daemon crashed without cleaning its PID file and the OS reused the PID, stop signals an unrelated same-user process.

**Fix:** Before signalling, confirm `proc_pid_path(pid)` matches `spec.binary_path`, as the nginx path already does.

### M6. Redis omitted from the `daemonizes` set — start reports unhealthy after succeeding

`src-tauri/src/commands/local_dev/supervisor.rs:846-849` vs `service_specs.rs:512-513`

The `daemonizes` match lists `DnsMasq | PhpFpm | Nginx` but not `Redis`, yet the redis spec is started with `--daemonize yes`. So `spawn_service` seeds the PID file with the forking parent PID (`:851`) and can `write_pid_file` / `return Ok(pid)` with that already-dead parent when TCP comes up before redis writes its own `--pidfile` (`:886-899`). The next `probe_running` reads the dead PID, fails adoption, and — redis not being nginx — reports `Unhealthy` / "port occupied but not owned by Badami" immediately after a successful start.

**Fix:** Add `ServiceKind::Redis` to the `daemonizes` match so health waits for the real `--pidfile`.

### M7. Postgres `SET search_path` — injection plus wrong-connection state

`src-tauri/src/commands/db_data.rs:317-321`

```rust
let set_stmt = format!("SET search_path TO {}", db_name);
```

`db_name` is interpolated with no quoting or escaping. Separately, it executes against the pool `p` rather than a dedicated connection, so the subsequent query at `:321` may run on a *different* pooled connection where the search_path never applied.

**Fix:** `p.acquire()` a single connection for both statements, and pass the schema as a quoted identifier or via `set_config('search_path', $1, false)` with a bind.

### M8. MySQL `USE` leaks schema context across pooled connections

`src-tauri/src/commands/db_data.rs:157-164,300-307`

``USE `db` `` is issued on a pooled connection that is then returned to the pool. A later call with `database == None` inherits the stale database context and silently runs against the wrong schema.

**Fix:** Fully qualify object names instead of relying on `USE`, or use a dedicated per-call connection that is reset on release.

### M9. Unescaped identifiers in two SQL builders

`src-tauri/src/commands/db_transfer.rs:508,510` — `format!("SHOW CREATE TABLE `{}`.`{}`", db, table)` doubles no backticks, unlike every other builder in the module.

`src-tauri/src/commands/db_schema.rs:663-667` — `dbc_drop_table` strips `' " ; \` but **not** the backtick, then quotes with backticks. A name like `` x`.`y `` changes which object is dropped.

**Fix:** Use `name.replace('`', "``")` inside backticks in both places, matching the rest of the codebase, rather than blacklist-stripping.

### M10. No connect timeout on SSH/SFTP

`src-tauri/src/commands/ssh.rs:84`, `sftp.rs:109`, `session_manager.rs:17`

```rust
let tcp = TcpStream::connect(&addr).map_err(|e| format!("Connection failed: {}", e))?;
```

Plain `TcpStream::connect` has no timeout and blocks on the OS default (tens of seconds) against a firewalled or dead host. `session.set_timeout` only covers post-handshake operations. FTP already does this correctly with `connect_timeout` (`ftp.rs:102`).

**Fix:** Resolve the address and use `TcpStream::connect_timeout`.

### M11. Unbounded buffering — OOM on large exports, files, and responses

- `db_transfer.rs:461` `fetch_all_rows` uses `fetch_all`, feeding `dbc_export_csv` / `_json` / `_sql`; `dbc_export_sql` additionally accumulates the whole dump in one `String` (`:127-196`) and `dbc_export_json` runs `to_string_pretty` over all rows (`:99-100`).
- `sftp.rs:364-366` `sftp_read_file` reads an entire remote file into a `String`.
- `ssh.rs:334` and `sftp.rs:629` `read_to_string` remote command stdout with no cap — a command emitting endless output fills RAM until the 30s timeout.
- `api.rs:240` `response.text()` with no size limit.

**Fix:** Stream exports with `sqlx::query(...).fetch(...)` writing incrementally; `stat` before `sftp_read_file` and reject oversized files; apply a byte budget to command output and HTTP response bodies.

### M12. Unbounded tab keep-alive retention

`src/components/layout/TabContentArea.tsx:71-113`

`mountedTabIds` grows on activation and is pruned only when a tab is *closed* (`:86-97`), never on deactivation. Every visited tab stays mounted (rendered `hidden`, `:60`) with all hooks live. N visited server tabs means N live SSH sessions, N xterm instances each with 10 000-line scrollback, and N one-second interval timers (`SshTerminal.tsx:274`) running behind hidden tabs, plus any Monaco/IDE instances.

Memory is reclaimed on close, so this is not a classic leak, but there is no LRU cap and hidden terminals keep re-rendering every second.

**Fix:** Cap mounted inactive tabs with LRU eviction, and pause per-second tickers when `!isActive`.

### M13. SSH auto-reconnect always passes null credentials

`src/hooks/useSshSession.ts:111-131`

The reconnect `invoke("ssh_connect", ...)` hard-codes `password: null, pemContent: null, passphrase: null`. For `password`, `pem_file`, `pem_saved`, and `pem_passphrase` auth this cannot succeed unless Rust caches credentials — so it exhausts `maxReconnectAttempts` with the backoff timer accomplishing nothing.

**Fix:** Capture the credentials passed to `connect()` in a ref and reuse them, or cache them per session on the Rust side.

### M14. Secrets are never zeroized

`src-tauri/src/commands/vault.rs:21,107,116,131,207`, `totp.rs:32`

```rust
encryption_key: Option<[u8; 32]>,   // plain array, no Zeroize
inner.encryption_key = None;        // vault_lock drops the key bytes un-wiped
password: String,                   // vault_unlock / vault_set_master_password
```

The long-lived key, master passwords, and decrypted plaintexts sit in ordinary heap and stack memory and are dropped without wiping — recoverable via swap, core dumps, or process-memory reads. `vault_lock` advertises "clear the encryption key from memory" but only drops it. `zeroize` is not in `Cargo.toml`.

**Fix:** Add `zeroize`; wrap the key in `Zeroizing<[u8;32]>`, take passwords as `Zeroizing<String>` or `SecretString`, and zeroize decrypted buffers after use.

### M15. Mutex poisoning turns one panic into a permanently dead subsystem

41 occurrences of `.lock().unwrap()` across `src-tauri/src` (e.g. `ssh.rs:71,165,185,241`; `sftp.rs:103,177,188`; `ftp.rs:67,119,129`; `file_watch.rs:87,96`), out of 166 total `unwrap()`/`expect()` calls. There is no `[profile]` section in `Cargo.toml`, so panics unwind rather than abort.

One panic while a lock is held poisons that mutex, and every subsequent `.lock().unwrap()` on it panics forever. The affected subsystem — all SSH, all SFTP, all FTP — stays dead until the app restarts.

**Fix:** Handle `PoisonError` by recovering the guard (`.unwrap_or_else(|e| e.into_inner())`) instead of `unwrap()`.

### M16. Corrupt IV crashes every decrypt command

`src-tauri/src/commands/vault.rs:201`, `credential.rs:163`

```rust
let nonce = Nonce::from_slice(iv);
```

`GenericArray::from_slice` **panics** when the slice length is not exactly 12. The IV arrives as an arbitrary `Vec<u8>` from IPC or from the database `iv` column. A truncated or corrupted row — including one produced by a sync conflict — panics `vault_decrypt`, `credential_decrypt_field`, `credential_copy_to_clipboard`, `totp_generate_code`, and `decrypt_pem_key` instead of returning an error.

**Fix:** Check `iv.len() == 12` and return `Err` before constructing the nonce.

### M17. TOTP `period: 0` causes a division-by-zero panic

`src-tauri/src/commands/totp.rs:52`

```rust
let remaining = period - (now % period);
```

`now % 0` is a division-by-zero panic in Rust, and `totp.generate(now)` divides by the step internally as well. `period` arrives from the frontend without validation.

**Fix:** Clamp `period` to a sane range (at least 1, realistically 15–300) before constructing the `TOTP`.

### M18. TOTP secret validation is looser than generation — secrets save, then never work

`src-tauri/src/commands/totp.rs:63-68` vs `:43`


The validator only checks base32 decodability, while `TOTP::new` additionally enforces the RFC 4226 minimum key length. ### M19. `VaultState` starts unlocked before `vault_init` runs

`src-tauri/src/commands/vault.rs:27-37`

```rust

    let machine_key = derive_machine_key();

}
```

The vault is fail-open by construction. Any `vault_encrypt` invoked before the frontend's `vault_init` completes silently encrypts under the machine key — even on an install where a master password *is* configured — producing rows the master key can never decrypt.

**Fix:** Initialize with `encryption_key: None, is_locked: true`, and only enter machine-key mode after `vault_init(false)` confirms no master password is set.

## LOW

**L0. AES-GCM is used without associated data.** `vault.rs:183-196` — nothing binds a ciphertext to the field or row it belongs to, so an attacker with database write access (or an unlucky sync conflict) can swap encrypted blobs between fields or records undetected. Pass the field/record ID as AAD via `Payload { msg, aad }`.

**L0b. `sqlx` is pinned to a version with a published advisory.** `Cargo.lock` resolves sqlx to **0.7.4**, affected by RUSTSEC-2024-0363 (binary-protocol misinterpretation via `i64` length truncation in the MySQL/Postgres drivers), fixed in 0.8.1. Exploitation requires payloads over 4 GiB, so practical risk here is low, but the upgrade is cheap.

**L0c. `derive_master_password_key` panics on a short salt.** `vault.rs:77-79` uses `.expect()` on `hash_password_into`, which errors with `SaltTooShort` for salts under 8 bytes. An empty or corrupted stored salt panics `vault_unlock` rather than returning an error. Validate `salt.len() >= 8` and propagate a `Result`.

**L1. Dead scaffold code.** `src/App.tsx` is still the default "Welcome to Tauri + React" `greet` demo. A grep confirms it is imported nowhere — `main.tsx` renders `AppWrapper`. Delete it; this also removes the only caller of the nonexistent `greet` command.

## Engineering recommendations

**No automated quality gate exists.** `.github/` contains only `copilot-instructions.md` — there are no workflows. `package.json` has no `test`, `lint`, or `typecheck` script, and there is no ESLint, Prettier, Biome, or Vitest configuration. The Rust side has 12 `#[cfg(test)]` modules; the frontend has none.

For a 73k-LOC application handling SSH private keys and database credentials, this is the highest-leverage structural gap. Minimum viable CI:

```yaml
- npx tsc --noEmit          # passes clean today — lock that in
- cargo clippy -- -D warnings
- cargo test
- cargo audit
- npm audit --audit-level=high
```

`tsc --noEmit` currently exits 0, so adding it to CI costs nothing and prevents regression.

**Reduce panic surface.** 166 `unwrap()`/`expect()` calls in backend code that processes untrusted remote input (SSH output, HTTP responses, database rows, CSV files). Prioritize the 41 `.lock().unwrap()` calls per M15, then the parsing paths.

**Documentation sprawl.** The repository root holds 11 plan/checklist documents totalling roughly 350 KB (`plan-local-dev.md` alone is 67 KB), plus a 220 KB `crash.txt`. `crash.txt` and `dist/` are correctly gitignored. Consider moving completed plans into `docs/archive/`.

## Suggested remediation order

Ordered by (impact × reachability) ÷ effort:

1. **C4** — sanitize `filename` in `ensure_temp_dir`. A four-line fix that closes remote-server-to-local-code-execution. Do this first; it is the cheapest fix with the worst consequence.
2. **C1 + C2 together** — re-key PEM storage through the OS keychain, then decide what is allowed to sync. This is the finding where an attacker who obtains the synced database gets SSH access to production servers.
3. **H1** — SSH host key verification. Small, self-contained; closes a live credential-theft path across three call sites.
4. **C3** — set a CSP and drop the `**` fs scope. Configuration-only changes.
5. **M1 + H7 together** — sentinel verification on unlock, then envelope encryption for rotation. These compound into total vault loss on a mistyped password, so fix them as one unit.
6. **H3** — parameterize the CSV importer and the cell/row builders.
7. **H4 + H5** — PID range validation, and re-resolving the nginx master inside the privileged shell.
8. **H6, M2** — keychain for the LLM API key; fix the two nonexistent RemoteIDE commands.
9. **M16–M19** — the input-validation panics (IV length, TOTP period, TOTP secret length, fail-open vault init). Individually small, collectively they remove a whole class of crash.
10. Add CI (`tsc --noEmit`, `cargo clippy`, `cargo test`, `cargo audit`, `npm audit`) so none of the above regresses, then work through the remaining medium findings.
