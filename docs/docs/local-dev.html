Local Dev

A complete local PHP stack on macOS: nginx, PHP-FPM in several versions, MariaDB, Redis, and dnsmasq, all from binaries Badami installs and manages. Nothing else has to be on the machine.

macOS only

Local Dev depends on macOS paths, launchd, and APFS. The module is hidden on Windows and Linux.

How it is put together

Everything Badami generates lives in one folder, so the stack is easy to inspect and easy to remove: 

~/Library/Application Support/Badami/local-dev/
├── runtime/          binaries, one folder per role and version
│   ├── nginx/1.25.4/
│   ├── php/7.4/      php and php-fpm side by side
│   ├── mariadb/10.11.6/
│   ├── redis/7.4.7/
│   └── dnsmasq/2.89/
├── data/mariadb/     the database files
├── config/valet/     tld, parks, per-site certificates
├── config/php/74/    php.ini per version
├── nginx/            nginx.conf, sites/*.conf
├── fpm/              one pool per PHP version
├── socks/            unix sockets nginx connects to
├── pids/  logs/      runtime state
└── valet-server/     the PHP router that maps a host to a site folder

Install a runtime

Open Local Dev → Settings → Runtime. The card lists every role and the versions installed for it, and marks which one is in use.

  1. Choose Add version. PHP 8.x comes from static-php-cli and dnsmasq from a Homebrew bottle; both are verified against a published checksum before anything is unpacked.
  2. Pick the version you want. It downloads, verifies, extracts, and then runs a version check against the new binary before committing it.
  3. Use Use on a row to switch which version a role runs, and the bin icon to remove one you no longer need.
PHP 7.4 has no upstream build

static-php-cli starts at 8.0, and there is no other neutral source that publishes a macOS arm64 build at a stable URL. Badami therefore reports 7.4 as unavailable for download rather than pointing at someone else's server. If you need 7.4, build it yourself and place it under runtime/php/7.4/.

Sites

A parked folder serves every direct subfolder as a site, the way a web root works. A linked site points at one specific folder.

Action Result
Park a directory Every subfolder becomes <folder>.test.
Link a project The project folder is served under its own name.
Isolate PHP Pins one site to a specific PHP version through its own pool.
Secure Issues a certificate from the local CA and serves the site over HTTPS.

HTTP and HTTPS

By default nginx binds an unprivileged port, so nothing runs as root:

Mode URL Requires admin
HTTP, default http://mysite.test:8080 No
HTTPS, per site https://mysite.test:8443 No
HTTP on port 80 http://mysite.test Yes, once, to install a LaunchDaemon

Port 80 is optional. Installing it writes a Badami-owned LaunchDaemon behind one admin prompt, and every config that daemon reads is rendered into a root-owned folder and verified by hash before the daemon is loaded.

Trusting the local CA

HTTPS works immediately, but browsers will warn until the local Certificate Authority is trusted. Settings → TLS shows the exact command it will run before the admin prompt appears, and the certificate is verified against a hash computed in the app before the keychain sees it.

Removing that trust is manual: use Keychain Access, or run security remove-trusted-cert against the CA file.

DNS for *.test

A resolver file alone is not working DNS: something has to answer on the port it points at. Badami checks by resolving a random label, not by looking for a file, and reports what it finds:

Mode What happens
Adopt An existing listener already answers for the TLD, so nothing is started.
Badami dnsmasq Installs a dnsmasq LaunchDaemon that binds port 53. One admin prompt.
High port Writes a resolver entry pointing at a non-privileged port, then runs dnsmasq unprivileged.
Degraded No working DNS. The stack still runs and sites answer on 127.0.0.1:8080 with a Host header, and the Doctor tab explains how to fix it.
Secure DNS in the browser

Chrome and Firefox can use DNS-over-HTTPS, which bypasses the resolver file entirely. Turn it off for *.test if the system probe is green but the browser cannot resolve your site.

Your database

MariaDB reads its files from data/mariadb. If you already have a datadir elsewhere, Settings → Runtime → Database files can move it in. On APFS the move is a clone, which shares blocks with the source instead of copying them: an 11 GB datadir moves in about a second and uses almost no extra disk.

The move verifies its work by hashing a sample of the copied files, always including ibdata1, and compares both sides. The source folder is never modified, so it stays available as a fallback until you delete it yourself.

Safety rules

  • Nothing is deleted automatically. Moving data clones it; removing a runtime version or a datadir is always an explicit action you take.
  • A binary is only used if its hash matches the manifest recorded when it was installed. A half-copied or altered file reads as absent rather than as working.
  • Starting MariaDB twice on one datadir is refused. Two servers writing the same InnoDB files is how databases get corrupted, so the guard is a hard failure with an explanation.
  • Privileged config is verified by hash. Root-owned nginx and dnsmasq configs are re-rendered, tokenized, checked against an allowlist, staged, and hash-verified before launchd loads them.

Uninstall

Local Dev → Settings → LaunchDaemon reverses what Badami installed: it removes only Badami-owned units and the staged config folder. The resolver file is removed only when you confirm and only when it carries Badami's marker, so a resolver file written by something else is left alone.

To remove the whole stack afterwards, delete the folder shown at the top of this page and the root-owned folder /Library/Application Support/Badami/local-dev-root/. Certificates you trusted must be removed from the keychain by hand, as described above.
